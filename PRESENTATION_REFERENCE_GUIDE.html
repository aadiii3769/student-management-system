3. Detailed File-by-File Breakdown

1. com.sims.Main.java

Role: Application bootstrap and entry point.

  • Sets the native OS Look and Feel via UIManager.setLookAndFeel(UIManager.getSystemLookAndFeelClassName()).
  • Enforces Swing threading safety by scheduling UI construction on the Event Dispatch Thread (EDT) via SwingUtilities.invokeLater().

2. com.sims.model.Student.java

Role: Plain Old Java Object (POJO) domain model.

  • Encapsulation: 11 private fields (studentId, rollNumber, fullName, email, phone, department, year, section, gender, dateOfBirth, address).
  • Provides public getters and setters, default constructor, parameterized constructor, and overrides equals(), hashCode(), and toString().

3. com.sims.dao.StudentDAO.java

Role: Data Access Object isolating all JDBC SQL persistence.

  • Exclusively uses PreparedStatement with bind variables (?) preventing SQL Injection.
  • Uses try-with-resources to guarantee automatic closure of statements and ResultSets.
  • Contains full CRUD operations: insert(), update(), delete(), findById(), findByRollNumber(), findAll(), and search().
  • Features automatic database self-healing: checks Oracle DB metadata on boot and auto-creates the STUDENTS table if missing.

4. com.sims.controller.StudentController.java

Role: Intermediary business logic controller (MVC).

  • Executes field-level validation using pre-compiled regular expression patterns.
  • Manages explicit transaction demarcation: conn.commit() on success, conn.rollback() on failure.
  • Provides CSV export via buffered character streams (BufferedWriter).

5. com.sims.view.StudentManagementFrame.java

Role: Complete graphical desktop interface.

  • Inherits from JFrame. Built with nested panels: Left form panel (GridBagLayout in TitledBorder) and right table panel.
  • Employs SwingWorker for offloading all database queries asynchronously off the EDT.
  • Registers observers: ActionListener (buttons), ListSelectionListener (table rows), DocumentListener (live search).

6. com.sims.util.DBConnection.java

Role: Creational Singleton managing the shared Oracle JDBC connection.

  • Double-Checked Locking (DCL) ensures safe thread-safe lazy instantiation.
  • Sets autoCommit = false for transaction control.
  • Automatically attempts port 1522 (Docker) and falls back to 1521 (Local Oracle XE).

7. com.sims.util.ValidationException.java

Role: Custom checked exception.

  • Inherits from java.lang.Exception. Contains a fieldName property allowing the View to auto-focus the offending input box.

4. Object-Oriented Programming (OOP) Concepts Demonstrated

1. Encapsulation

All model attributes are declared private. The external world cannot directly mutate a student's internal state without going through public accessor and mutator methods. Constructors and database connection states are similarly encapsulated.

2. Inheritance

Inheritance (is-a relationship) is utilized across the application:

  • StudentManagementFrame extends JFrame: Reuses top-level windowing, title bar, and OS event dispatch capabilities.
  • ValidationException extends Exception: Inherits checked exception capabilities and stack-trace recording from Java's standard library.
  • Anonymous worker instances extend SwingWorker<List<Student>, Void> for thread pooling.

3. Polymorphism

Both fundamental types of polymorphism are demonstrated:

  • Compile-Time Polymorphism (Method Overloading):
    • Constructor overloading in Student (default vs. full field initialization).
    • Constructor overloading in ValidationException.
    • Method overloading: deleteStudent(long id) vs. deleteStudentByRoll(String roll).
  • Runtime Polymorphism (Method Overriding):
    • Overriding paintComponent(Graphics g) in JButton for custom anti-aliased rendering.
    • Overriding isCellEditable(int row, int col) in DefaultTableModel.
    • Overriding getTableCellRendererComponent() in DefaultTableCellRenderer for zebra striping.
    • Overriding doInBackground() and done() in SwingWorker.

4. Abstraction & Interfaces

Concrete implementations are decoupled from callers through standard Java interfaces:

  • ActionListener, DocumentListener, ListSelectionListener abstract UI event delivery.
  • JDBC interfaces (java.sql.Connection, PreparedStatement, ResultSet) allow our Java code to interact with Oracle without depending on vendor-proprietary internal classes.

5. Design Patterns Implemented (Academic Defense)

Pattern Category Pattern Name Class Academic Defense & Justification
Creational Singleton DBConnection Establishing a database connection incurs expensive socket handshakes and process allocations. The Singleton pattern guarantees that exactly one shared connection exists across the entire JVM lifecycle.
Structural Data Access Object (DAO) StudentDAO Isolates all SQL queries and JDBC operations. If database tables are altered or migrated from Oracle to PostgreSQL, only StudentDAO is modified; all controllers and views remain intact.
Behavioral Observer Swing Listeners The View does not hardcode business workflows upon user interaction. Instead, UI components publish events to registered observers (ActionListeners) that delegate to the Controller.
Architectural Model-View-Controller (MVC) Full System Separates data representation (Model), user display (View), and business processing (Controller), maximizing code reusability, testability, and maintainability.

6. GUI Frameworks in Java: How Swing Operates

1. AWT vs. Swing vs. JavaFX

  • AWT (Heavyweight): Relied on native OS C/C++ peer widgets. Appearance varied drastically between platforms.
  • Swing (Lightweight): 100% pure Java. Components are drawn using Java 2D graphics. Offers pluggable Look and Feel, rich components (JTable, JSplitPane), and uniform cross-platform behavior.
  • JavaFX: Modern rich-client platform using CSS and XML (FXML).

2. Why Null/Absolute Layouts Are Forbidden

Using setLayout(null) and setBounds() causes severe display corruption when run on screens with different resolutions, DPI scaling, or operating system font metrics. Standard layout managers dynamically compute component dimensions:

  • BorderLayout: Centers the main table and anchors toolbars.
  • GridBagLayout: Arranges label-field pairs cleanly in rows and columns with strict alignment constraints.
  • FlowLayout & GridLayout: Organizes toolbars and uniform button grids.

3. The Event Dispatch Thread (EDT) and Threading

Swing is strictly single-threaded: all UI painting and user events run on the Event Dispatch Thread (EDT).

Critical Concept: Executing a slow database query on the EDT locks the GUI, causing the window to freeze. SIMS uses SwingWorker to execute SQL on background threads (doInBackground) and safely publishes results back to the EDT (done).

7. Step-by-Step Trace: What Happens When You Click "Add Student"?

  1. User Interaction: User fills out form fields and clicks + Add Student.
  2. Observer Dispatched: Button fires ActionEvent to the registered listener method onAddStudent().
  3. Data Extraction: readStudentFromForm() reads field text, parses LocalDate, and encapsulates values into a Student POJO.
  4. Worker Scheduled: A SwingWorker instance is scheduled off the EDT.
  5. Controller Validation: StudentController.addStudent() runs:
    • Regex validates Roll Number, Full Name, Email, and 10-digit Phone.
    • Calculates student age (15–70) via java.time.Period.
    • Calls studentDAO.findByRollNumber() to guarantee no duplicate roll number exists.
  6. JDBC Execution: studentDAO.insert() binds parameters to an INSERT INTO STUDENTS ... PreparedStatement.
  7. Transaction Commit: Database executes SQL; Controller issues conn.commit() to ensure atomic persistence.
  8. EDT Update: SwingWorker.done() runs back on the EDT, displays a success dialog, clears form fields, and reloads the table asynchronously.

8. Top Viva Questions & Model Answers

Q1: Why did you use PreparedStatement instead of Statement?
Answer: Statement compiles SQL with raw string concatenation, exposing the application to SQL Injection vulnerabilities. PreparedStatement pre-compiles the SQL template and treats user parameters strictly as literal values (?). It also provides performance benefits through database execution-plan caching.
Q2: Why is autoCommit disabled in your DBConnection?
Answer: When autoCommit is true, every individual DML statement commits immediately. Setting autoCommit = false enables manual transaction management in the Controller layer. We can execute complex operations atomically and call conn.commit() only if all steps succeed, or conn.rollback() if an exception occurs.
Q3: How does SwingWorker maintain UI responsiveness?
Answer: Swing's Event Dispatch Thread (EDT) must never be blocked by high-latency tasks like database network I/O. SwingWorker runs the JDBC operations in doInBackground() on a background thread pool, and subsequently executes done() back on the EDT to safely update the DefaultTableModel without UI freezing.
Q4: Why did you create a custom ValidationException?
Answer: ValidationException is a checked exception that carries domain-specific failure details, including the exact field name that failed. This enables the UI layer to catch the exception, display a clear warning dialog, and automatically set focus to the offending input field.
Q5: What makes your DBConnection thread-safe?
Answer: We implemented Double-Checked Locking (DCL) with a volatile instance variable. The volatile keyword prevents CPU instruction re-ordering, ensuring that any thread accessing getInstance() sees a fully constructed connection object.
